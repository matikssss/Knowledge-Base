## 01. Основы Git и три зоны

### 01/50. Что такое Git и какую задачу он решает?

**Ответ:** **Git** — распределённая система контроля версий. Она позволяет фиксировать изменения проекта, хранить историю, работать в ветках, объединять результаты разработки и при необходимости возвращаться к прежним состояниям.

**Механизм:** каждый разработчик может иметь локальный репозиторий с историей коммитов. Создавать локальные коммиты можно без подключения к серверу; обмен выполняется отдельно, например через `push` и `fetch`.

> [!important] Не путай
> Git — инструмент контроля версий. GitHub и GitLab — платформы, на которых можно размещать Git-репозитории и организовывать совместную работу.

### 02/50. Что такое репозиторий Git?

**Ответ:** **Репозиторий Git** — хранилище истории версий проекта: коммитов, объектов Git, ссылок на ветки и служебных данных.

**Механизм:** в обычном локальном репозитории служебные данные находятся в каталоге `.git/`, а рабочие файлы — рядом с ним. Существуют и *bare*-репозитории без обычного рабочего каталога — их часто используют на серверах.

```bash
git init
git status
```

### 03/50. Что такое рабочий каталог в Git?

**Ответ:** **Рабочий каталог (Working Tree)** — файлы и папки проекта на диске, с которыми мы непосредственно работаем: редактируем, создаём и удаляем.

**Механизм:** изменение файла в редакторе сначала меняет Working Tree. Само по себе это ещё не готовит его к коммиту и не создаёт запись в истории.

### 04/50. Что такое индекс Git?

**Ответ:** **Индекс (Index, Staging Area)** — промежуточная область подготовки следующего коммита. В ней Git хранит, какие версии файлов войдут в будущий снимок проекта.

```text
Working Tree  --git add-->  Index  --git commit-->  локальная история
```

**Пример:** `nginx.conf` в HEAD содержит `80`, в индексе — `8080`, а в рабочем каталоге — `5000`. Если сейчас выполнить `git commit`, в коммит попадёт **`8080`**, а не `5000`.

> [!tip] Ключевая мысль
> `git add` не записывает новый коммит. Он подготавливает конкретную версию изменений для следующего коммита.

### 05/50. Чем `git init` отличается от `git clone`?

**Ответ:** `git init` создаёт новый локальный Git-репозиторий в существующей папке (первоначально без коммитов). `git clone` создаёт локальную копию существующего репозитория, получает его историю и обычно настраивает удалённый репозиторий `origin`.

```bash
git init
git clone https://example.com/team/project.git
```

**Важно:** `clone` не просто копирует видимые файлы: он также получает необходимые Git-объекты и ссылки для работы с историей (если не заданы специальные ограничения клонирования).

### 06/50. Что именно делает `git add`?

**Ответ:** `git add` добавляет в индекс выбранное состояние файла или изменений, подготавливая их для следующего коммита.

```bash
git add nginx.conf   # Подготовить конкретный файл
git add .            # Подготовить изменения в текущем каталоге и ниже
git add -A           # Учесть добавления, изменения и удаления во всём репозитории
```

**Нюанс:** после `git add nginx.conf` можно снова изменить файл. Тогда версия в индексе и версия в Working Tree будут различаться.

### 07/50. Что сохраняет `git commit`?

**Ответ:** `git commit` создаёт новый объект коммита — фиксирует **снимок подготовленного в индексе состояния проекта** и метаданные: автора, сообщение, время и ссылку(и) на родительский коммит. Затем обычно передвигает указатель текущей ветки на новый коммит.

```bash
git commit -m "fix(nginx): correct upstream port"
```

**Важно:** коммит не обязан включать все изменения из Working Tree — только то, что подготовлено в индексе. Git хранит данные эффективно с помощью объектов и повторного использования неизменившегося содержимого.

### 08/50. Когда изменения попадают в локальную историю Git?

**Ответ:** После успешного `git commit`. `git add` только подготавливает изменения, а `git push` отдельно публикует локальные коммиты в удалённый репозиторий.

```text
Редактирование → git add → git commit → git push
 Working Tree       Index      история     сервер
```

### 09/50. Каким должен быть хороший коммит?

**Ответ:** Хороший коммит — **небольшое логически завершённое изменение**, которое можно понять, проверить и при необходимости отдельно отменить. Сообщение ясно объясняет смысл изменения.

**Пример:** `fix(nginx): correct proxy port` вместо `fix stuff`.

**Практика:** по возможности не смешивать несвязанные задачи, не коммитить пароли и временные файлы, проверять результат. «Маленький» — не значит «одна строка»: важнее **одна осмысленная задача**.

### 10/50. Каков обычный путь изменения от файла до удалённого репозитория?

**Ответ:** Изменяем файл в **Working Tree** → готовим через `git add` в **Index** → фиксируем через `git commit` в **локальной истории** → публикуем через `git push` в **удалённом репозитории**.

```bash
# Например, после изменения nginx.conf:
git status
git add nginx.conf
git commit -m "fix: update nginx configuration"
git push origin main
```

**Важно:** `push` отправляет необходимые коммиты и обновляет удалённую ссылку ветки, если сервер разрешает операцию. Пропускать `add` для новой правки нельзя: Git коммитит подготовленное состояние.

### 11/50. Что показывает `git status`?

**Ответ:** `git status` показывает текущее состояние репозитория: ветку, подготовленные и неподготовленные изменения, неотслеживаемые файлы, наличие конфликтов и, при настроенном upstream, соотношение с отслеживаемой веткой.

```bash
git status
git status -sb   # Краткий вывод, включая информацию о ветке
```

**Важно:** `status` не загружает актуальные сведения с сервера — информация о `origin/main` может быть устаревшей до `fetch`.

### 12/50. Чем отличаются `git diff` и `git diff --staged`?

**Ответ:** `git diff` сравнивает **Working Tree с Index** (неподготовленные изменения отслеживаемых файлов); `git diff --staged` сравнивает **Index с HEAD** (изменения, подготовленные к коммиту).

```text
HEAD:         listen 80;
Index:        listen 8080;
Working Tree: listen 5000;
```

```bash
git diff             # 8080 → 5000
git diff --staged    # 80 → 8080
git diff HEAD        # 80 → 5000 (суммарно по отслеживаемым файлам)
```

> [!warning] Частая ловушка
> `git diff` обычно **не показывает содержимое новых неотслеживаемых файлов**. После `git add new.txt` его содержимое появится в `git diff --staged`.

### 13/50. Для чего нужен `.gitignore`?

**Ответ:** `.gitignore` задаёт шаблоны файлов, которые Git не должен автоматически предлагать к отслеживанию, если они ещё не отслеживаются. Обычно это временные файлы, логи, сборочные артефакты, локальные настройки.

```gitignore
*.log
.env
__pycache__/
dist/
```

**Важно:** `.gitignore` — не средство защиты опубликованных секретов и не удаляет файлы из старой истории коммитов.

### 14/50. Почему добавление файла в `.gitignore` не скрывает уже отслеживаемый файл?

**Ответ:** Правила `.gitignore` применяются прежде всего к **неотслеживаемым** файлам. Если файл уже находится под контролем Git, он остаётся отслеживаемым.

```bash
# Перестать отслеживать файл, но сохранить его на диске:
git rm --cached .env
# Добавить .env в .gitignore, затем:
git add .gitignore
git commit -m "chore: stop tracking local env file"
```

**Важно:** `.env` останется доступен в предыдущих коммитах; если в нём был настоящий секрет — **сначала отозвать или заменить секрет**.

## 02. Ветки, HEAD и история

### 15/50. Что такое ветка Git?

**Ответ:** **Ветка Git** — подвижный указатель на коммит, позволяющий вести отдельную линию разработки без немедленного объединения её изменений с другими ветками.

```text
C0 ── C1 ── C2 (main)
       \
        C3 ── C4 (feature)
```

**Механизм:** если текущая ветка `feature` создаст коммит `C5`, указатель `feature` переместится на `C5`, а `main` останется на `C2`.

### 16/50. Что обозначает HEAD в Git?

**Ответ:** **HEAD** — специальный указатель текущего положения Git. Обычно он ссылается на текущую ветку, а через неё — на её последний коммит.

**Detached HEAD:** в этом состоянии HEAD указывает **непосредственно на коммит**, а не на ветку. Новые коммиты можно создавать, но никакая ветка автоматически не сдвигается.

```bash
git switch main               # HEAD обычно ссылается на main
git switch --detach <хеш>    # HEAD указывает прямо на коммит
```

### 17/50. Как создать ветку и сразу переключиться на неё?

**Ответ:** `git switch -c <имя_ветки>` создаёт новую ветку от текущего коммита и сразу делает её текущей.

```bash
git switch -c feature/healthcheck
# Старый эквивалент:
git checkout -b feature/healthcheck
```

**Нюанс:** `git branch feature/healthcheck` создаёт ветку, но **не переключает** на неё.

### 18/50. Как быстро посмотреть историю веток и их связи?

**Ответ:** Использовать графический текстовый вывод `git log` с ключами `--graph --oneline --decorate --all`.

```bash
git log --oneline --graph --decorate --all -20
git branch -avv
```

`--graph` отображает разветвления, `--decorate` — указатели веток и тегов, `--all` — историю, доступную через все показанные ссылки, `-20` ограничивает вывод. Это **не графический интерфейс**, а схема истории прямо в терминале.

## 03. Удалённые репозитории и SSH

### 19/50. Что такое remote в Git?

**Ответ:** **Remote** — настроенное имя-ссылка на другой Git-репозиторий, обычно расположенный на сервере. Например, `origin` — распространённое имя удалённого репозитория.

```bash
git remote -v
git remote add origin <URL>
```

**Важно:** `origin` — не особая команда или обязательное имя, а условное название, которое можно изменить.

### 20/50. Что такое `origin/main`?

**Ответ:** `origin/main` — **локальная remote-tracking ссылка**, отражающая известное твоему Git положение ветки `main` удалённого репозитория `origin` на момент последнего получения данных.

```text
main         → твоя локальная ветка
origin/main  → локальное представление удалённой main
```

**Важно:** `origin/main` — не «живая» ссылка на сервер. Обычно она обновляется после `git fetch`, а `main` при этом не обязательно изменяется.

### 21/50. Как понять, чем локальная `main` отличается от `origin/main`?

**Ответ:** Сначала получить актуальное состояние удалённых ссылок через `git fetch origin`, затем сравнить направления истории и, если нужно, содержимое файлов.

```bash
git fetch origin

# Коммиты, которые есть только на серверной стороне:
git log --oneline main..origin/main

# Коммиты, которые есть только в локальной main:
git log --oneline origin/main..main

# Кратко: сколько коммитов только слева и только справа:
git rev-list --left-right --count main...origin/main

# Разница конечных состояний файлов:
git diff main origin/main
```

**Важно:** `git diff main origin/main` показывает разницу в содержимом, а не всю историю расхождения. Две ветки могут иметь разную историю, но одинаковые конечные файлы.

### 22/50. Чем `git fetch` отличается от `git pull`?

**Ответ:** `git fetch` скачивает новые коммиты и обновляет remote-tracking ссылки **без автоматического объединения с текущей веткой**. `git pull` сначала делает `fetch`, а затем интегрирует изменения в текущую ветку через merge или rebase согласно параметрам и настройкам.

```bash
git fetch origin
git pull --ff-only origin main
```

**Важно:** `git pull` не всегда создаёт merge-коммит: поведение зависит от выбранного режима (`--ff-only`, `--rebase`, `--no-rebase`) и конфигурации.

### 23/50. Что делает `git push -u origin feature/login`?

**Ответ:** Отправляет локальную ветку `feature/login` в удалённый репозиторий `origin` (создаёт удалённую ветку при необходимости) и настраивает её **upstream** — связь для отслеживания удалённой ветки.

```bash
git push -u origin feature/login
# После настройки обычно можно использовать:
git push
git pull
```

`-u` означает `--set-upstream`. Upstream — это не сам `origin`, а конкретная отслеживаемая ветка, например `origin/feature/login`.

### 24/50. Что делает `git pull --rebase`?

**Ответ:** Сначала получает удалённые изменения (`fetch`), затем переносит локальные коммиты текущей ветки поверх актуальной upstream-истории с помощью `rebase`, вместо создания обычного merge-коммита.

**Пример:** локально `C1 → L1`, удалённо `C1 → R1`. После успешного `git pull --rebase` получается `C1 → R1 → L1*`: локальный коммит воспроизведён и может получить новый хеш.

```bash
git pull --rebase
# При конфликте:
git status
# Исправить файлы, git add ...
git rebase --continue
# Или полностью отменить перебазирование:
git rebase --abort
```

> [!warning] Осторожно
> Коммиты, которые rebase действительно переприменил, получают новые идентификаторы. Не следует без согласования переписывать историю, на которой уже основана работа коллег. Если возможно простое перемещение указателя, новые коммиты могут не создаваться.

### 25/50. Зачем GitLab использует пару SSH-ключей?

**Ответ:** Пара SSH-ключей позволяет **безопасно аутентифицировать пользователя при подключении к GitLab** без передачи личного приватного ключа серверу. Публичный ключ добавляют в GitLab, приватный хранится только у владельца.

**Механизм:** клиент с помощью приватного ключа подтверждает владение им; сервер проверяет подпись с помощью соответствующего публичного ключа. SSH также шифрует сетевое соединение.

```bash
ssh-keygen -t ed25519 -C "work-laptop"
ssh -T git@gitlab.com
```

**Важно:** `~/.ssh/id_ed25519` — **приватный** ключ, его никому нельзя отправлять. `~/.ssh/id_ed25519.pub` — **публичный**, его можно добавлять в GitLab. Реальные имена файлов зависят от выбранного пути при генерации.

## 04. Слияние, rebase и конфликты

### 26/50. Что такое слияние fast-forward?

**Ответ:** **Fast-forward merge (FF)** — слияние, при котором Git просто передвигает указатель текущей ветки на коммит объединяемой ветки **без создания merge-коммита**. Оно возможно, когда текущий коммит является предком коммита объединяемой ветки.

```text
До:    C0 ── C1 (main) ── C2 ── C3 (feature)
После: C0 ── C1 ───────── C2 ── C3 (main, feature)
```

```bash
git switch main
git merge --ff-only feature    # Разрешить только FF
```

**Важно:** если объединяемая ветка уже полностью является предком текущей, Git сообщит `Already up to date`; это успешная операция без изменений. `git merge --no-ff feature` создаёт отдельный merge-коммит даже при возможности FF, если есть что объединять.

### 27/50. Когда Git создаёт коммит слияния?

**Ответ:** При обычном `git merge` Git создаёт **merge-коммит**, если линии истории разошлись и простой Fast-forward невозможен. Merge-коммит обычно имеет **двух родителей**: текущий коммит целевой ветки и коммит объединяемой ветки. `--no-ff` позволяет создать его и при доступном FF.

```text
До:       C2 ── C3 (feature)
         /
    C0─ C1
         \
          C4 ── C5 (main)

После:    C2 ── C3 (feature)
         /       \
    C0─ C1        C6 (main)
         \       /
          C4 ── C5
```

**Механизм:** на новом `C6` окажется снимок итогового состояния файлов и ссылки на родителей `C5` и `C3`. Указатель `main` перейдёт на `C6`; `feature` останется на `C3`. История исходных коммитов не переписывается.

**Дополнение:** стратегия `octopus` может создать merge-коммит с **более чем двумя родителями** при объединении нескольких веток; чаще используется для простых, не конфликтующих слияний.

### 28/50. Чем `merge` отличается от `rebase`?

**Ответ:** **Merge** объединяет существующие линии истории, **сохраняя исходные коммиты и их идентификаторы**; при разветвлении обычно создаёт merge-коммит. **Rebase** повторно применяет уникальные коммиты выбранной (обычно текущей) ветки на новой основе; переприменённые коммиты получают новые идентификаторы, а история часто становится линейной.

```text
Исходно:       C2 ── C3 (feature)
              /
         C0─ C1
              \
               C4 ── C5 (main)

После rebase (из feature: git rebase main):
         C0─ C1─ C4─ C5─ C2*─ C3* (feature)
                       ↑
                      main
```

**Важно:** `git rebase main`, запущенный в `feature`, **не переносит коммиты в main** — он перестраивает **feature поверх main**. Сама `main` не перемещается. Конфликты могут возникать во время повторного применения отдельных коммитов.

### 29/50. Почему опасно выполнять `rebase` опубликованной общей ветки?

**Ответ:** Rebase переписывает историю переприменённых коммитов и меняет их идентификаторы. Если на старую опубликованную историю уже опираются другие разработчики, их ветки разойдутся с новой историей. Для публикации переписанных коммитов может понадобиться принудительный push, который при ошибке способен исключить чужие изменения из удалённой ветки.

**Причинная цепочка:** `rebase → новые хеши → расхождение историй → обычный push может быть отклонён → опасность неверного force-push`.

**Важно:** rebase собственных **ещё не опубликованных** коммитов — обычная полезная практика. Переписывание общей истории согласовывают с командой; `--force-with-lease` уменьшает риск, но не отменяет необходимость проверки.

### 30/50. Каков порядок разрешения конфликта слияния?

**Ответ:** Проверить конфликтующие файлы через `git status`, открыть их, вручную выбрать корректное итоговое содержимое и удалить конфликтные маркеры. Затем `git add` пометить конфликты как разрешённые, выполнить тесты и завершить слияние коммитом.

```bash
git status
# Открываем конфликтующий файл, исправляем:
# <<<<<<< HEAD
# ...
# =======
# ...
# >>>>>>> feature

git add nginx.conf
git merge --continue  # Либо git commit, если merge ожидает завершения
```

**Важно:** не выбирай автоматически «нашу» или «их» версию, не разобрав смысл изменений. Конфликт — это ситуация, когда Git не смог корректно объединить изменения автоматически; исправленный результат нужно проверить.

### 31/50. Как прервать неудачное слияние или перебазирование?

**Ответ:** Во время незавершённого merge используют `git merge --abort`, а во время незавершённого rebase — `git rebase --abort`. Они пытаются вернуть состояние к моменту до начала соответствующей операции.

```bash
git merge --abort
# ИЛИ, если идёт rebase:
git rebase --abort
```

**Важно:** `--abort` не отменяет произвольный старый merge-коммит, который уже создан и опубликован. При предварительно существовавших несохранённых правках полное восстановление не всегда гарантировано — важные изменения лучше сохранить до операции.

## 05. Отмена изменений и восстановление

### 32/50. Как отменить незакоммиченные изменения одного файла?

**Ответ:** Для отслеживаемого файла `git restore <файл>` отменяет **неподготовленные** изменения в рабочем каталоге, восстанавливая содержимое из индекса. Подготовленные в индексе изменения при этом остаются.

```bash
git restore nginx.conf
```

**Пример:** HEAD = `80`, Index = `8080`, Working Tree = `5000`. После `git restore nginx.conf` получим `80 / 8080 / 8080`.

> [!danger] Осторожно
> Неподготовленные изменения файла будут потеряны, если их больше нигде не сохранили. `git restore` без дополнительных флагов не служит для удаления новых неотслеживаемых файлов.

### 33/50. Как убрать файл из индекса, сохранив изменения в рабочем каталоге?

**Ответ:** Если нужно **снять изменения с подготовки к коммиту** (*unstage*), используй `git restore --staged <файл>`. Он восстанавливает индекс из HEAD, но **не изменяет рабочий файл**.

```bash
git restore --staged nginx.conf
```

**Пример:** HEAD = `80`, Index = `8080`, Working Tree = `5000`. После команды будет `80 / 80 / 5000`.

**Отдельный случай:** если требуется **совсем перестать отслеживать файл**, сохранив его на диске, используют `git rm --cached <файл>` и затем коммитят удаление из индекса. Это **не то же самое**, что простое `restore --staged`.

### 34/50. Чем отличаются `git reset --soft`, `--mixed` и `--hard`?

**Ответ:** Все три варианта перемещают HEAD (обычно вместе с указателем текущей ветки) на выбранный коммит, но по-разному обращаются с индексом и рабочими файлами.

| Режим | HEAD / текущая ветка | Index | Working Tree |
|---|---|---|---|
| `--soft` | Перемещается | Не меняется | Не меняется |
| `--mixed` | Перемещается | Приводится к целевому коммиту | Не меняется |
| `--hard` | Перемещается | Приводится к целевому коммиту | Отслеживаемые файлы приводятся к целевому коммиту |

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

**Важно:** `--mixed` — режим по умолчанию для `git reset <коммит>`. Варианты с перемещением ветки не следует бездумно использовать для переписывания опубликованной общей истории.

### 35/50. Почему `git reset --hard` считается опасной командой?

**Ответ:** `git reset --hard` не только перемещает ветку/HEAD, но и перезаписывает индекс и отслеживаемые рабочие файлы состоянием указанного коммита. Поэтому **незакоммиченные изменения могут быть потеряны**.

```bash
git status            # Сначала проверить
git reset --hard HEAD~1  # Опасно, если нужны текущие правки
```

**Нюанс:** старые **коммиты** иногда можно найти через `git reflog`, но потерянные **незакоммиченные** изменения `reflog` не обязан сохранять. Кроме того, `--hard` может удалить неотслеживаемые файлы/каталоги, если они мешают восстановить отслеживаемые пути.

### 36/50. Как безопасно отменить уже опубликованный коммит?

**Ответ:** Обычно используется `git revert <хеш>`: команда создаёт **новый коммит с изменениями, отменяющими изменения выбранного коммита**, не удаляя старые коммиты из истории. Затем результат отправляют обычным `git push`.

```bash
git revert <хеш_ошибочного_коммита>
git push origin main
```

**Пример:** `C0—C1—C2—C3` → `git revert C2` → `C0—C1—C2—C3—C4`, где `C4` отменяет изменения `C2`.

**Важно:** `revert C2` **не возвращает весь проект в состояние C1**. Он применяет обратное изменение к текущему состоянию, поэтому конфликты возможны. Для отмены merge-коммита нужен отдельный выбор основного родителя (`git revert -m 1 <хеш>`), и последствия следует анализировать.

### 37/50. Когда применяют `git commit --amend`?

**Ответ:** `git commit --amend` используют, чтобы **исправить последний коммит**: изменить его сообщение и/или включить дополнительно подготовленные изменения. Git создаёт вместо прежнего **новый коммит с новым хешем**.

```bash
# Исправить сообщение последнего коммита:
git commit --amend -m "fix: correct nginx port"

# Добавить забытый файл в последний коммит:
git add nginx.conf
git commit --amend --no-edit
```

**Важно:** лучше применять к локальному неопубликованному последнему коммиту. После публикации `amend` переписывает историю и требует согласования с коллегами.

### 38/50. Для чего используется `git stash`?

**Ответ:** `git stash` временно сохраняет незакоммиченные изменения в специальном локальном хранилище, позволяя освободить рабочий каталог и позже продолжить работу без обычного коммита в истории ветки.

```bash
git stash push -u -m "WIP: nginx setup"  # -u включает untracked
git stash list
git stash apply 'stash@{0}'             # Применить; запись оставить
git stash pop                            # Применить; запись удалить при успехе
```

**Нюансы:** обычный stash захватывает подготовленные и неподготовленные изменения **отслеживаемых** файлов. Новые untracked-файлы включаются через `-u`; ignored-файлы — нет (для них существует `-a`). `pop --index` пытается восстановить также исходное состояние индекса. При конфликтах stash-запись обычно остаётся.

### 39/50. Для чего нужен `git reflog`?

**Ответ:** **`git reflog`** — локальный журнал перемещений Git-ссылок, в том числе HEAD. Он помогает найти хеш ранее доступного коммита после `reset`, `rebase`, переключений и других операций, даже если коммит исчез из обычного `git log` текущей ветки.

```bash
git reflog -10
git reflog show main
```

**Важно:** журнал локальный, не передаётся коллегам через push и не хранится бесконечно. Он не является надёжной резервной копией незакоммиченных данных.

### 40/50. Как восстановить найденный через `reflog` потерянный коммит?

**Ответ:** Найти его хеш через `git reflog` и **создать ветку на этом коммите**, сохранив доступ к нему и его предкам. Затем проверить восстановленную историю.

```bash
git reflog -10
# Например, нашли потерянный коммит abc1234:
git branch backup/recovered abc1234
git log --oneline backup/recovered -5
git switch backup/recovered
```

**Если нужно вернуть `main`:** после проверки, когда `main` осталась предком восстановленного коммита, можно выполнить `git switch main && git merge --ff-only backup/recovered`.

**Важно:** создание ветки на найденном коммите **уже восстанавливает доступ к истории**; дополнительные `git add` / `git commit` для этого не нужны.

### 41/50. Что делает `git cherry-pick <commit>`?

**Ответ:** `git cherry-pick <хеш>` берёт изменение, внесённое выбранным коммитом, и **повторно применяет его в текущей ветке**, обычно создавая новый коммит с новым идентификатором. Остальные коммиты исходной ветки не переносятся автоматически.

```text
До:      C1 ── C2 ── C3 (feature)
        /
       C0 ── C4 (main)

После cherry-pick C2 из main:
       C0 ── C4 ── C2* (main)
        \
         C1 ── C2 ── C3 (feature)
```

```bash
git switch main
git cherry-pick <хеш_C2>
# При конфликте: исправить файлы → git add →
git cherry-pick --continue
# Отмена:
git cherry-pick --abort
```

**Важно:** переносится **изменение**, а не исходная связь коммита с родителями. Если изменение уже применено, коммит может оказаться пустым; если зависит от других коммитов, возможен конфликт.

### 42/50. Почему `git push --force-with-lease` безопаснее `git push --force`?

**Ответ:** `--force` принудительно обновляет удалённую ветку без обычного требования Fast-forward, что может исключить чужие коммиты из её истории. `--force-with-lease` дополнительно проверяет, что удалённая ветка **всё ещё указывает на ожидаемый коммит**, и отклоняет отправку, если её положение неожиданно изменилось.

```bash
git push --force-with-lease origin feature/login
```

**Важно:** это **не абсолютная защита**: например, автоматический фоновый `fetch` может обновить локальное представление удалённой ссылки, и простой `--force-with-lease` перестанет защищать от некоторых неожиданных сценариев. При критичных операциях можно явно указать ожидаемый хеш: `--force-with-lease=refs/heads/feature/login:<ожидаемый_хеш>`. Не переписывай общие ветки без согласования.

## 06. Диагностика и безопасность

### 43/50. Как найти коммит, в котором появилась ошибка, среди большой истории?

**Ответ:** Использовать **`git bisect`** — бинарный поиск первого коммита, на котором заданная ошибка воспроизводится. Указываем заведомо исправный и проблемный коммиты, затем проверяем предложенные Git промежуточные версии вручную либо автоматически через `git bisect run`.

```bash
git bisect start
git bisect bad HEAD
git bisect good <хеш_исправного_коммита>
# Проверить текущую предложенную версию:
git bisect good   # Работает
git bisect bad    # Ошибка есть
# После нахождения проблемного коммита:
git bisect reset
```

```bash
# Автоматический пример: скрипт возвращает 0, если тест проходит,
# и ненулевой код, если тест выявил проблему:
git bisect run ./test.sh
```

**Важно:** нужен надёжный критерий «работает / сломано». Коммит первого **проявления** ошибки не обязательно содержит всю первоначальную причину: например, новая маршрутизация могла активировать ошибочную старую настройку Nginx.

### 44/50. Что показывает `git blame <файл>`?

**Ответ:** `git blame` показывает для каждой строки текущей версии файла **коммит, который последним изменил эту строку**, а также автора и дату, связанные с этим изменением. Помогает понять происхождение конкретной строки и найти контекст изменения.

```bash
git blame nginx.conf
git blame -L 2,5 nginx.conf   # Только строки со 2-й по 5-ю
git show <хеш_из_blame>     # Посмотреть сам коммит
```

**Важно:** `blame` не определяет, кто виноват в баге. Если ошибка была заложена раньше или строку только переформатировали, ответ может потребовать дальнейшего анализа. Для некоторых сценариев полезен `git blame -w` (игнорировать изменения пробельных символов).

### 45/50. Что делать, если секрет случайно попал в Git?

**Ответ:** Если секрет опубликован, **в первую очередь немедленно отозвать или заменить его**. Затем удалить его из текущего кода, настроить безопасное хранение, проверить доступы и журналы на признаки использования секрета. При необходимости согласовать с командой очистку истории Git и проверить копии/артефакты.

**Алгоритм:** отозвать пароль/токен → оценить последствия утечки → удалить секрет из проекта и настроить `.gitignore`/хранилище секретов → при необходимости согласовать очистку истории и уведомить ответственных.

> [!danger] Главное
> Удаление файла, новый коммит и `.gitignore` **не делают опубликованный секрет безопасным**: его уже могли скопировать. Даже приватный репозиторий не гарантирует, что секрет никому не стал доступен. Для production-секрета это возможный инцидент безопасности.

### 46/50. Какие команды выполнить перед исправлением непонятной проблемы Git?

**Ответ:** Сначала выполнить **диагностику без разрушительных действий**: проверить состояние файлов и индекса, текущую ветку, удалённые адреса, историю и локальные перемещения HEAD. Только после этого выбирать способ исправления.

```bash
git status
git branch --show-current
git remote -v
git log --oneline --graph --decorate --all -20
git reflog -20
# Если нужны свежие сведения о сервере:
git fetch origin
```

**Важно:** перед `reset --hard`, `clean`, переписыванием истории и force-push сначала определить цель и сохранить нужные изменения. `git fetch` обновляет сведения об удалённом репозитории, но не сливает их в текущую ветку.

## 07. Командные процессы и инструменты

### 47/50. Что такое Git hooks?

**Ответ:** **Git hooks** — исполняемые скрипты или программы, которые Git вызывает при определённых событиях, например перед коммитом, при проверке сообщения коммита или перед отправкой изменений. Они позволяют автоматически проверять код и запускать дополнительные действия.

| Hook | Когда выполняется | Пример применения |
|---|---|---|
| `pre-commit` | Перед созданием коммита | Проверка форматирования |
| `commit-msg` | Перед окончанием создания коммита | Проверка формата сообщения |
| `pre-push` | Перед отправкой | Запуск тестов |
| `post-commit` | После коммита | Локальные уведомления |

Посмотреть доступные hooks:

```bash
ls -la .git/hooks
```

Пример содержимого исполняемого файла `.git/hooks/pre-commit`:

```sh
#!/bin/sh
git diff --cached --check
```

Чтобы включить его в Linux:

```bash
chmod +x .git/hooks/pre-commit
```

**Важно:** локальные hooks обычно лежат в `.git/hooks/` (или пути из `core.hooksPath`), не передаются стандартным `push` как часть истории и могут быть обойдены. Обязательные проверки дублируют в CI/CD и правилах сервера.

### 48/50. Как выглядит сообщение в формате Conventional Commits?

**Ответ:** **Conventional Commits** — соглашение о формате сообщения `type(scope): description`: тип изменения, необязательная область и краткое описание. Формат удобен для читаемой истории, changelog и автоматизации версионирования.

```text
fix(nginx): correct upstream port
feat(api): add healthcheck endpoint
ci: add tests for pull requests
docs: update deployment guide
feat(api)!: remove legacy endpoint
```

**Типы:** `feat` — новая возможность, `fix` — исправление ошибки, `docs` — документация, `ci` — CI/CD. Дополнительные типы (`chore`, `refactor`, `test` и т. п.) определяются соглашениями проекта.

**Важно:** `!` перед двоеточием или footer `BREAKING CHANGE:` обозначают нарушение обратной совместимости. Формат не гарантирует качества самих изменений; его можно проверять через `commit-msg` hook или CI.

### 49/50. Что такое Git submodule?

**Ответ:** **Git submodule** — механизм подключения одного Git-репозитория внутрь другого с **сохранением их отдельных историй**. Основной репозиторий хранит ссылку на **конкретный коммит** подмодуля, а не автоматически использует его последнюю версию.

```bash
# Добавить подмодуль:
git submodule add <URL_репозитория> deploy-scripts
git add .gitmodules deploy-scripts
git commit -m "chore: add deployment submodule"

# Получить проект с подмодулями:
git clone --recurse-submodules <URL_проекта>

# Если основной проект уже клонирован:
git submodule update --init --recursive

# Увидеть состояние:
git submodule status
```

**Механизм:** `.gitmodules` хранит путь и URL, а запись `gitlink` в дереве основного коммита — идентификатор закреплённого коммита подмодуля. Чтобы обновить ссылку, выбирают новую версию внутри подмодуля, затем в основном проекте делают `git add <путь>` и `git commit`.

**Важно:** по умолчанию `git submodule update` часто приводит к Detached HEAD внутри подмодуля. Обновление внешнего репозитория **не обновляет автоматически** закреплённый коммит основного проекта.

### 50/50. В чём идея trunk-based разработки?

**Ответ:** **Trunk-based development** — стратегия разработки, при которой небольшие изменения **часто объединяют в основную ветку** (`main`, *trunk*). Для этого используют прямую работу с trunk либо короткоживущие ветки, быстрые проверки и частую интеграцию.

**Зачем:** меньше длительных расхождений истории, проще слияния, проще организовать Continuous Integration. Незавершённую функциональность иногда скрывают **feature flags**.

**Важно:** `merge в main` ≠ `deployment в production` ≠ `release пользователям`. Код можно объединить, но пока не развернуть; можно развернуть, но оставить функцию отключённой до релиза.

**Сравнение:** в классическом GitFlow выделяют дополнительные долгоживущие ветки (`main`, `develop`) и отдельные процессы релиза; trunk-based ориентирован на частую интеграцию в одну основную линию.

### Мини-схема трёх зон

```text
    Локальная история (HEAD)
              │
              │ git restore --staged file
              ▼
          Index / Stage
              ▲             │
       git add file          │ git restore file
              │             ▼
            Working Tree

Git commit: Index → новый снимок в локальной истории
Git push:   опубликование локальных коммитов на сервере
```

Условная схема направлений, не полный список всех команд и параметров.

### Как не перепутать три способа «отмены»

- **`restore`** — меняет рабочий файл и/или индекс; сам по себе не создаёт коммит.
- **`reset`** — перемещает указатель текущей ветки/HEAD (в соответствующем режиме также индекс и Working Tree); может переписать видимую историю ветки.
- **`revert`** — создаёт новый коммит с отменой изменений указанного коммита, сохраняя прежнюю историю.

## 09. Типичные ловушки собеседования

1. **«HEAD всегда указывает на ветку».** Нет: Detached HEAD указывает прямо на коммит.
2. **«`git add` сохраняет версию в истории».** Нет: он готовит состояние в индексе, история меняется после `commit`.
3. **«`git diff` показывает вообще все новые файлы».** Нет: содержимое untracked обычно не выводится.
4. **«`origin/main` — текущее состояние сервера в реальном времени».** Нет: это локальная remote-tracking ссылка, которая может устареть.
5. **«`git pull` всегда делает merge-коммит».** Нет: возможны FF, rebase, иной режим.
6. **«`merge` всегда создаёт merge-коммит».** Нет: при FF достаточно сдвинуть указатель.
7. **«`git rebase main` из feature переносит коммиты в main».** Нет: перебазируется feature, main остаётся на месте.
8. **«`reset --hard` можно полностью отменить через reflog».** Для старых коммитов часто да, для уничтоженных незакоммиченных файлов — не гарантируется.
9. **«`revert C2` возвращает весь проект к C1».** Нет: отменяет изменения отдельного коммита, применённые к текущему состоянию.
10. **«`cherry-pick` объединяет истории».** Нет: повторно применяет выбранные изменения без сохранения исходных родительских связей.
11. **«`--force-with-lease` делает принудительный push совершенно безопасным».** Нет: это дополнительная проверка ожидаемого указателя, а не гарантия сохранения всей чужой работы.
12. **«Удалили `.env` и добавили `.gitignore` — утечки больше нет».** Нет: сначала отзыв/смена секрета; старые копии могли сохраниться.
13. **«Submodule автоматически обновляется до последней версии».** Нет: основной проект закрепляет конкретный коммит.
14. **«Слили с main — сразу выпустили в production».** Нет: merge, deployment и release — разные события.
15. **«`git blame` определяет виновного».** Нет: показывает историю изменения строки, но не первопричину бага.
